# DSH Mobile v1.4.9

> 这一版处理的都是「引擎起不来 / 起来了又卡住」这类最影响使用的问题。
> 其中重启卡死由社区贡献者 **@henryz78** 定位并修复，特此致谢。

## 1. 重启后永久卡住 —— 已修复（社区贡献 @henryz78）

**现象**：点「重启」后一直停在「正在启动」，等多久都不动；只能杀掉 App 重来。

**根因**：监督器的 `stopping` 标志在 `stop()` 里置位，但 `start()` 里**没有清零**。于是新拉起的监督循环第一轮就判断「应该停止」，一次都不执行 —— 状态永远停在 `Starting`。

影响面比「重启卡住」更大：**任何一次停止**（服务被系统回收、通知栏退出、切换权限模式）之后，这个进程里就再也启动不了引擎，只能杀 App。

修复还处理了第二层竞态：旧循环被取消是异步的，而 `catch (Exception)` 会把 `CancellationException` 一起吞掉，于是旧循环可能在复位后继续跑完收尾，把新循环刚设的状态覆盖成「退避中」。现在退出判断同时检查协程是否还活着。

**真机验证**：连续点三次重启，分别用 10.2 秒、13.2 秒恢复，`boot.log` 记录完整（旧代码第一轮就会卡死）。

## 2. 等几十分钟引擎都准备不好 —— 已修复

**现象**：更新后打开 App，遮罩转几十分钟都进不去。

**根因**：不是单个 bug，而是多层自动修复各自有边界、**组合起来没有总预算**。算一下就明白：

```
每轮 = 45s 健康检查 + 20s 插件探针 + 退避
14 轮 ≈ 21 分钟    20 轮 ≈ 30 分钟
```

触发这条路径的是「插件探针报告异常 → 摘掉一个插件 → 重启」。旧代码在这里会把退避计数**重置为 0**、当轮**没有延迟**、且**不计入**重启上限 —— 于是可以无限循环。v1.4.7 的一个探针误报（拿一行已被禁用的配置去比对）让这类用户从「自愈中」变成「稳定失败循环」。

**修复**：

- 新增 **5 分钟启动总时限**：超时直接给出可操作的错误提示，不再后台空转；
- 插件自动隔离的重启改走统一退避，**最多 3 次**，超了就停在「降级但可用」状态；
- 进入健康状态后重置计时与额度 —— 只约束「这一次启动」，不影响长期运行的设备。

## 3. 三处「无限等待」加了超时

这三处比无限重试更糟，因为它们会让监督循环**永久停住**，连日志都不再写：

| 位置 | 原问题 | 现在 |
|---|---|---|
| Shizuku 命令执行 | 读输出和等待退出都没有超时 | 读流放后台线程 + 超时后返回已读内容 |
| Root 模式启动前备份 | `tar` 打包每轮都跑，无超时 | 60 秒预算，超时丢弃本次备份并继续启动 |
| 端口清理脚本 | 遍历 `/proc` 杀进程，无超时 | 3 秒预算 |

## 4. `corepack` 入口被覆盖 —— 已修复

**现象**（用户报告，定位很准）：`corepack` 命令报 SyntaxError；直接执行会无限自循环。

**根因**：不是判断逻辑写错，而是**硬链接写穿**。

Termux 的 npm 把 `bin/corepack` **硬链接**到 `dist/corepack.js`（同一个 inode）。构建脚本用 `cat > bin/corepack` 生成启动器，而 shell 的 `>` 是**截断已存在的文件**而不是新建 —— 于是写的是共享 inode，源 JS 被一并覆盖成 shell 脚本。

这完美解释了为什么只有 `corepack` 一个坏：其余 6 个（npm / npx / pnpm / pnpx / yarn / yarnpkg）的 `bin` 与 `dist` 不共享 inode。

**修复三层**：构建期先断开链接再写 + 写后校验；运行期检测并还原已装出去的旧包；两份源运行时产物就地修复。

## 5. Root 模式新增路径提示

开启 Root 模式时的第二次确认里，现在明确写了：

> - 不要**在应用目录（`files/engine`、`files/dsh-home`）或工作区目录里手动改动、移动、删除文件。
> - root 进程写出的文件属主是 root、权限位收紧，App 自身随后**读不了**；症状是「插件加载失败」「引擎起不来」，往往只能清数据或重装才能恢复。
> - 你自己的文件（文档、代码、项目）请放在**外部文件夹**（如 `Documents/`），让 AI 在那里工作。
> - 确实要改应用内的东西，请用应用自己的设置或插件，而不是 root 文件管理器。

## 6. Agent 环境说明修正

原来写的是「不要安装 glibc/native 二进制」，容易被理解成原生模块完全不可用。现在改为区分：

- **glibc 预编译包**（`sharp` 的 linux-x64 包等）❌ 不可用
- **源码编译** ✅ 可行（用户实测 better-sqlite3 + SQLite 3.53.4 + ELF arm64 编译成功）
