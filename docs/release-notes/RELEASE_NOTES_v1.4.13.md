# DSH Mobile v1.4.13

> **紧急修复**：v1.4.12 把 PTC 模式（`run_code` 工具）弄坏了。如果你在用 PTC，请尽快更新。

## PTC 模式报 `libz.so.1 not found` —— 已修复

**现象**：v1.4.12 之后，PTC 模式（`run_code`）一用就失败：

```
CANNOT LINK EXECUTABLE ".../files/engine/bin/node":
library "libz.so.1" not found
```

引擎主进程正常，只有 PTC 的子进程起不来。

### 原因

这是我 v1.4.12 引入的回归，说清楚：

Android 上没有 `ldconfig`，Termux 构建的 node 找 `libz` 这类库全靠 `LD_LIBRARY_PATH` 环境变量。而 PTC 模式启动子进程时，会**清空几乎所有继承的环境变量**，只保留一份白名单 —— 里面原本没有 `LD_LIBRARY_PATH`，所以子进程找不到库。

这个问题我们在 v1.4.9 修过（把它加进白名单 + 无条件注入）。但 v1.4.12 我把构建切到了「去重后的运行时包」，**那份包是在加这个补丁之前生成的** —— 于是补丁整体丢失，老问题原样回归。

### 更该反省的地方

补丁只存在于「某一个 zip 产物」里，**没有进入构建流程**。所以只要换了源包，补丁就静默消失，而且构建、测试全绿，完全看不出来。

现在把它接进构建了：每次打包都会检查补丁的两处改动是否都在，缺了就现场补上；补完还缺就**直接中止构建**，绝不把坏包发出去。

### 验证

在模拟器里做了对照实验（模拟 PTC 子进程的启动环境）：

| 环境 | 结果 |
|---|---|
| 带 `LD_LIBRARY_PATH` | node 正常执行 ✅ |
| 不带 | `CANNOT LINK EXECUTABLE ... libz.so.1 not found` ← 正是你报的错 |

也就是说，补丁在不在，就是这个报错的开关。

另外把构建流程也验了一遍：故意换回未打补丁的包 → 构建日志出现「PTC 补丁缺失，正在应用… → PTC 补丁已应用」，自动兜住了。
